# Полный аудит кода Monopoly Telegram Mini App

## 1. БАГ-ОШИБКИ (логические, рантайм, несоответствия правилам)

### 1.1 КРИТИЧЕСКИЕ

**[BUG-01] In-memory store не работает на Vercel вообще**
- **Файл:** `api/game.js`, строки 8–18
- **Проблема:** Vercel Serverless Functions — stateless. Каждый вызов может (и будет) обслуживаться разным инстансом. `const rooms = new Map()` **гарантированно теряет данные** между запросами. Это не "ограничение для разработки" — это полная неработоспособность в продакшене.
- **Последствия:** После создания комнаты следующий запрос `state` или `join` с высокой вероятностью получит `Room not found`.

**[BUG-02] Аукцион: таймер проверяется только при клиентском polling**
- **Файл:** `api/game.js`, case `auction_check`; `public/index.html`, `renderAuction()`
- **Проблема:** Аукцион завершается только когда **кто-то** вызовет `auction_check`. Если все клиенты закроют вкладку или потеряют связь, аукцион висит вечно. Более того, интервал `auctionInterval` на клиенте создаётся только у того, кто видит аукцион — остальные узнают о завершении только через общий polling (2.5 сек), что создаёт окно для race condition.
- **Правила:** «После каждой новой ставки таймер сбрасывается на 10 секунд. Если за 10 секунд не поступает новых ставок — завершается.»

**[BUG-03] Дубль — игрок не получает повторный бросок корректно**
- **Файл:** `api/game.js`, case `endturn`, строки ~380–390
- **Проблема:** 
```javascript
if (room.lastDice[0] === room.lastDice[1] && !currentPlayer.inJail && currentPlayer.doublesCount > 0) {
  room.turnPhase = 'roll';
```
После покупки/аукциона/оплаты аренды `doublesCount` может быть уже сброшен (в ветке `!isDoubles` стоит `currentPlayer.doublesCount = 0`). Но если был дубль, `doublesCount` увеличивается до 1–2, и при вызове `endturn` условие сработает. **Однако**: если игрок попал в тюрьму из-за клетки "В ТЮРЬМУ", `turnPhase` будет `'endturn'`, и при вызове `endturn` проверка `!currentPlayer.inJail` не сработает — но `lastDice` всё ещё дубль. Это ок. Но: если карточка Шанс отправила в тюрьму, `lastDice` будет от последнего броска (дубль), а `inJail = true` — тоже ок. 

**Настоящий баг:** при 3-м дубле подряд игрок отправляется в тюрьму и `turnPhase = 'endturn'`. При `endturn` проверяется `room.lastDice[0] === room.lastDice[1]` — true! И `!currentPlayer.inJail` — false (уже в тюрьме). Ок, это работает. Но `doublesCount` не сбрасывается после тюрьмы по дублям — только `jailTurns = 0`. При выходе из тюрьмы `doublesCount` остаётся > 0, что может дать неверный повторный бросок.

**Фикс:**
```javascript
// В case 'roll', когда игрок попадает в тюрьму:
currentPlayer.doublesCount = 0; // добавить эту строку
```

**[BUG-04] `checkPostMove` вызывает сам себя рекурсивно при картах перемещения — потенциальный бесконечный цикл**
- **Файл:** `api/game.js`, функция `checkPostMove`
- **Проблема:** Карта "Шанс" может переместить на другую клетку "Шанс" (поз. 7 → карта "move to 36" теоретически). В текущих картах `CHANCE_CARDS` нет "переместитесь на клетку Шанс", но если игрок перемещается на позицию 10 (Тюрьма/посещение), позицию 0 (Старт) — это безопасно. Но карта `{ type: 'move', to: 39, text: 'Отправляйтесь на Петровку' }` перемещает на Петровку, а потом `checkPostMove` проверяет — если Петровка занята, начисляет аренду. Это корректно.

**Реальная проблема:** Карта `{ type: 'move', to: 10 }` ("Посетите тюрьму без ареста") — при `checkPostMove` на позиции 10 (`type: 'jail'`) — клетка не описана в switch как property/tax/chance/chest/gotojail, поэтому попадает в финальный `room.turnPhase = 'endturn'`. Ок.

**Но:** карта `{ type: 'move', to: 5 }` ("Отправляйтесь на Рижскую ж/д") — если ж/д уже куплена, `checkPostMove` начислит аренду. При этом `diceSum` передаётся из оригинального броска, что корректно для ж/д (не зависит от кубиков). Для коммунальных предприятий — если карта перемещает на utility, `diceSum` используется корректно.

**Однако:** нет защиты от рекурсии. Добавьте guard:
```javascript
function checkPostMove(room, player, diceSum, depth = 0) {
  if (depth > 5) { room.turnPhase = 'endturn'; return; }
  // ... внутри рекурсивных вызовов передавать depth + 1
}
```

**[BUG-05] Проход через Старт при перемещении картой — неверная логика**
- **Файл:** `api/game.js`, `processCardEffect`, строка с `if (card.to < player.position && card.to !== 10)`
- **Проблема:** Если игрок стоит на позиции 36 и карта перемещает на позицию 5 (Рижская ж/д), `card.to < player.position` = true, значит +200$. Это корректно. Но если игрок на позиции 3 и карта перемещает на позицию 0 (Старт), `card.to < player.position` = true, и `card.to !== 10` = true, значит +200$. Но перемещение с 3 на 0 **проходит через Старт** (двигаясь назад? или вперёд через всё поле?). В классической Монополии карта "Отправляйтесь на Старт" **всегда** даёт 200$. Но перемещение "назад" на 3 клетки не должно давать 200$. Исключение `card.to !== 10` — ad hoc. 

**Правильная логика:** Карты перемещения в Монополии всегда двигают вперёд, и если номер целевой клетки меньше текущей — значит прошли через Старт. Исключение — карта "В тюрьму" (но та имеет `type: 'jail'`, не `type: 'move'`). Текущая логика в целом корректна, но исключение для позиции 10 некорректно: если карта "Посетите тюрьму", это не "арест", а "просто посещение" — в классике 200$ за проход через Старт **дают**. Удалите `&& card.to !== 10`.

**[BUG-06] Банкротство не проверяет фактическую невозможность покрыть долг**
- **Файл:** `api/game.js`, case `bankrupt`
- **Проблема:** Игрок может объявить банкротство в любой момент, когда `turnPhase === 'manage'`, без проверки, что он действительно не может покрыть долг. Злоумышленник может объявить банкротство с положительным балансом (или с имуществом, которое можно заложить), чтобы передать имущество союзнику.
- **Правила:** «Если после всех возможных залогов и продаж баланс всё ещё отрицательный — остаётся только объявить банкротство.»
- **Фикс:** На сервере проверять, что `canPlayerRecover(player) === false` перед разрешением банкротства.

**[BUG-07] `distributeRent` дважды начисляет деньги владельцу**
- **Файл:** `api/game.js`, `checkPostMove` → `distributeRent`
- **Проблема:** В `checkPostMove`:
```javascript
player.balance -= rent;
distributeRent(room, cell.id, rent, player.id);
```
А в `distributeRent`, если нет deal:
```javascript
const owner = getPlayerById(room, prop.ownerId);
if (owner) owner.balance += rent;
```
Это корректно — деньги снимаются у гостя и начисляются владельцу. **Но:** при наличии deal, если плательщик — участник deal (`deal.members.includes(payerId)`), проверка в `checkPostMove` уже пропускает аренду:
```javascript
if (deal && deal.members.includes(player.id)) {
  room.turnPhase = 'endturn';
  return;
}
```
Ок, это корректно.

**Однако:** `distributeRent` проверяет `!deal.members.includes(payerId)`, а если payerId — участник deal — деньги идут owner напрямую. Но мы не должны сюда попасть, потому что ранее уже return. Ок, нет бага.

**[BUG-08] При аренде с monopoly deal, rent уже списан у игрока, но `distributeRent` в ветке "normal" не проверяет наличие deal для данного cellId**
- **Файл:** `api/game.js`, `distributeRent`
- **Проблема:** `getMonopolyDealForCell` ищет deal по `cell.color`. Но deal может не включать владельца текущей клетки (если он вышел из deal). В этом случае `deal.members.includes(payerId)` = false, и деньги будут распределены по deal.members, которые **не включают** фактического владельца. Owner не получит ничего.
- **Фикс:** Проверять, что `deal.members.includes(prop.ownerId)` перед распределением через deal.

**[BUG-09] Покупка при недостаточном балансе — нет перехода к аукциону**
- **Файл:** `api/game.js`, case `buy`
- **Проблема:** Если `balance < price`, сервер возвращает ошибку, но клиент всё равно показывает кнопку "Купить". Игрок не может ни купить, ни отказаться (кнопка аукциона показывается, это ок). Но проблема: на клиенте кнопка "Купить" не дизейблится при недостатке средств.

**[BUG-10] `endturn` после `payjail` — turnPhase не обновляется для roll**
- **Файл:** `api/game.js`, case `payjail`
- **Проблема:** После оплаты 50$ за выход из тюрьмы, `turnPhase` остаётся неопределённым (не устанавливается в `'roll'`). Если баланс >= 0, нет установки `turnPhase = 'roll'` — игрок не может бросить кубик.
- **Правила:** После выхода из тюрьмы за деньги игрок бросает кубик и двигается.
- **Фикс:**
```javascript
case 'payjail': {
  // ... existing code ...
  currentPlayer.inJail = false;
  currentPlayer.jailTurns = 0;
  if (currentPlayer.balance >= 0) {
    room.turnPhase = 'roll'; // ← ДОБАВИТЬ
  }
  // ...
}
```

**[BUG-11] `usejailcard` — после использования карты turnPhase не устанавливается в 'roll'**
- **Файл:** `api/game.js`, case `usejailcard`
- **Аналогично BUG-10:** После `inJail = false`, `turnPhase` не меняется. Он остаётся `'roll'` (потому что карту используют до броска). Подождите — `room.turnPhase` проверяется в `payjail`: `if (room.turnPhase !== 'roll')`. Значит `usejailcard` вызывается на фазе `'roll'`, и после неё `turnPhase` остаётся `'roll'`. Ок, это корректно для `usejailcard`. Но для `payjail` — нет, потому что там нет проверки: серверная проверка `if (room.turnPhase !== 'roll')` есть, значит `payjail` вызывается на фазе `'roll'`, и после оплаты `turnPhase` остаётся `'roll'`. **Ок, нет бага для usejailcard/payjail** — turnPhase остаётся 'roll'.

Но подождите, в case `payjail`:
```javascript
if (currentPlayer.balance < 0) {
  room.turnPhase = 'manage';
}
```
Если баланс >= 0, `turnPhase` остаётся `'roll'` (не менялся). **Это корректно.** Снимаю BUG-10.

**[BUG-12] Аренда за utility: `diceSum` при перемещении картой**
- **Файл:** `api/game.js`, `checkPostMove` + `processCardEffect`
- **Проблема:** Когда карта перемещает игрока на utility, `checkPostMove` вызывается с оригинальным `diceSum`. По правилам Монополии, при перемещении на utility по карте Шанс, игрок должен бросить кубики заново для расчёта аренды (или платить 10× бросок). В текущей реализации используется `diceSum` из последнего реального броска. Это несоответствие правилам, но допустимое упрощение. Стоит документировать.

**[BUG-13] Залог улицы с домами на соседних участках группы**
- **Файл:** `api/game.js`, case `mortgage`
- **Проблема:** Проверяется только `prop.houses > 0`, но не проверяется, есть ли дома на **других** улицах той же цветовой группы. По правилам Монополии, нельзя заложить улицу, если в этой группе есть дома. Нужно сначала продать все дома в группе.

const cell = BOARD[cellId];
if (cell.color) {

  const hasHousesInGroup = group.some(cid => (room.properties[cid]?.houses || 0) > 0);

**[BUG-14] `canPlayerRecover` на клиенте неточен**
- **Файл:** `public/index.html`, функция `canPlayerRecover`
- **Проблема:** Используется hardcoded `+= prop.houses * 25` вместо реального расчёта (houseCost / 2). Данные `BOARD_DATA` на клиенте не содержат `price` и `houseCost`. Также `BOARD_DATA[cellId]?.price` undefined — в клиентском `BOARD_DATA` нет поля `price`.
- **Последствия:** Клиент может неверно определить, нужно ли показывать кнопку "Банкротство", что приведёт к зависанию хода.

**[BUG-15] Двойной проход через Старт при обычном ходе**
- **Файл:** `api/game.js`, case `roll`
- **Проблема:** В ветке doubles:
```javascript
const oldPos = currentPlayer.position;
currentPlayer.position = (currentPlayer.position + diceSum) % 40;
if (currentPlayer.position < oldPos) currentPlayer.balance += 200;
```
А потом `checkPostMove` может вызвать `processCardEffect` с `card.to < player.position` — и добавить ещё 200$. Пример: игрок на позиции 38, бросает 5, попадает на 3 (прошёл Старт, +200$). Позиция 3 — property "Нагатинская", свободная. Покупает. Ок.

Но если позиция 3 — "Казна" (позиция 2 — Казна, позиция 3 — property). Если попадает на позицию 7 (Шанс) и карта "Отправляйтесь на Старт" → `card.to = 0`, `0 < 7` → true → +200$. Итого 400$ за один ход? Это корректно по правилам Монополии — прошёл Старт при движении + прошёл Старт по карте.

**Нет бага**, это правильное поведение.

**[BUG-16] Аукцион при банкротстве (method === 'auction') — не реализован**
- **Файл:** `api/game.js`, case `bankrupt`, method `auction`
- **Проблема:** Комментарий говорит "simplified: return to bank for now" — аукцион не реализован, имущество просто удаляется. Это противоречит правилам.
- **Правила:** «Выставить на аукцион — всё имущество поочередно или единым лотом уходит с молотка по правилам обычного аукциона.»

**[BUG-17] Передача имущества при банкротстве — нет оплаты**
- **Файл:** `api/game.js`, case `bankrupt`, method `transfer`
- **Проблема:** Имущество передаётся бесплатно. По правилам: «получатель обязан выкупить их по цене, предложенной системой». Нет никакой оплаты.
- **Последствия:** Сговор — игрок может намеренно обанкротиться и бесплатно передать всё союзнику.

**[BUG-18] `nextTurn` при банкротстве текущего игрока — двойной вызов**
- **Файл:** `api/game.js`, case `bankrupt`
```javascript
if (getActivePlayer(room).id === playerId) {
  nextTurn(room);
}
// ...
room.turnPhase = room.state === 'finished' ? 'finished' : (getActivePlayer(room).id === playerId ? 'roll' : room.turnPhase);
```
- **Проблема:** После `nextTurn(room)`, `getActivePlayer(room)` возвращает НОВОГО игрока, а `playerId` — банкрот. Условие `getActivePlayer(room).id === playerId` после `nextTurn` будет false (банкрот уже не active). Поэтому `room.turnPhase` не меняется на `'roll'`, а остаётся каким был (возможно `'manage'`). Новый игрок не сможет начать ход.
- **Фикс:**
```javascript
if (getActivePlayer(room).id === playerId) {
  nextTurn(room);
}
room.turnPhase = room.state === 'finished' ? 'finished' : 'roll';
```

**[BUG-19] Карта "В тюрьму" из Казны/Шанс — `checkPostMove` не вызывается для новой позиции**
- **Файл:** `api/game.js`, `processCardEffect`
- **Проблема:** При `card.type === 'jail'`, позиция ставится 10, `inJail = true`. В `checkPostMove` далее проверяется `if (player.inJail) { room.turnPhase = 'endturn'; return; }` — **нет такой проверки!** После `processCardEffect`, код продолжается:
```javascript
if (player.inJail) { room.turnPhase = 'endturn'; return; }
```
Ок, эта проверка есть в `checkPostMove` в ветках `chance`/`chest`. Работает.

**[BUG-20] При `method === 'transfer'` в банкротстве дома не сбрасываются**
- **Файл:** `api/game.js`, case `bankrupt`
- **Проблема:** При `method === 'bank'` и `method === 'auction'` дома удаляются (property удаляется целиком). При `method === 'transfer'` свойства переходят целиком **с домами**. Это по правилам корректно (получатель получает улицы с застройками), но нужно убедиться, что получатель имеет полную группу для сохранения домов. В текущем коде это не проверяется.

## 2. ПРОБЛЕМЫ АРХИТЕКТУРЫ И НАДЁЖНОСТИ

**[ARCH-01] In-memory storage несовместим с Vercel** (КРИТИЧЕСКИЙ)
- Vercel Serverless Functions — stateless. Каждый cold start = пустой `Map()`. Даже в одном инстансе данные теряются при простое ~15 минут.
- **Решение:** Мигрировать на Upstash Redis (`@upstash/redis`). `@vercel/kv` deprecated с декабря 2024.

**[ARCH-02] Race conditions при параллельных запросах**
- Два игрока одновременно делают ставку на аукционе → оба читают одинаковый `currentBid` → оба проходят проверку → последний записывает свою ставку, перезатирая первую (lost update).
- **Решение:** При Redis — использовать `WATCH`/`MULTI` или Lua-скрипты для атомарных операций. Или оптимистическая блокировка через version counter.

**[ARCH-03] Нет очистки старых комнат**
- Комнаты никогда не удаляются из хранилища. При переходе на Redis — нужен TTL (например, 24 часа).

**[ARCH-04] Polling каждые 2.5 секунды — неэффективно**
- 6 игроков × 2.5 сек = 144 запроса/мин. Каждый запрос возвращает полное состояние комнаты (десятки KB).
- **Решение:** WebSocket (через Ably/Pusher/Liveblocks), или Server-Sent Events, или хотя бы long polling с ETag/version comparison.

**[ARCH-05] Отсутствие версионирования состояния**
- Клиент перезаписывает `currentRoom` при каждом polling, даже если ничего не изменилось. При одновременном действии и polling — возможно мерцание UI (действие обновило UI, потом polling вернул старое состояние до того как сервер обработал действие).

**[ARCH-06] `auctionInterval` и `pollInterval` не очищаются при выходе/ошибке**
- **Файл:** `public/index.html`
- При навигации между экранами интервалы не останавливаются. `pollInterval` работает даже на экране меню. `auctionInterval` не очищается при закрытии modal или при переподключении.

**[ARCH-07] Нет reconnection logic**
- Если пользователь перезагрузит страницу или переоткроет mini app, он окажется на экране меню, хотя комната всё ещё активна. Нет механизма "вернуться в игру".

## 3. УЯЗВИМОСТИ БЕЗОПАСНОСТИ

**[SEC-01] Нет валидации Telegram initData** (КРИТИЧЕСКИЙ)
- **Файл:** `api/game.js`
- `playerId` приходит в body запроса и никак не верифицируется. Любой может подделать запрос с чужим `playerId` и выполнить действия от его имени (бросить кубик, купить, объявить банкротство).
- **Решение:** Передавать `Telegram.WebApp.initData` в header, валидировать HMAC на сервере через bot token.
- **Пример:**
```javascript
const crypto = require('crypto');
function validateInitData(initData, botToken) {
  const params = new URLSearchParams(initData);
  const hash = params.get('hash');
  params.delete('hash');
  const sorted = [...params.entries()].sort().map(([k,v]) => `${k}=${v}`).join('\n');
  const secret = crypto.createHmac('sha256', 'WebAppData').update(botToken).digest();
  const computed = crypto.createHmac('sha256', secret).update(sorted).digest('hex');
  return computed === hash;
}
```

**[SEC-02] XSS через имена игроков**
- **Файл:** `public/index.html`, `renderGame()`, `renderLobby()`, `renderNotifications()`
- Имена игроков вставляются через `innerHTML` без экранирования:
```javascript
`<span>${p.name.substring(0, 8)}</span>`
```
- Если Telegram username содержит `<script>` или HTML (маловероятно, но возможно через подделку запроса без валидации initData), XSS атака.
- **Фикс:** Использовать `textContent` или sanitize:
```javascript
function esc(str) { return str.replace(/[&<>"']/g, c => ({'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c])); }
```

**[SEC-03] Манипуляция аукционом — bid validation**
- **Файл:** `api/game.js`, case `auction_bid`
- Проверяется `amount > bidder.balance`, но `amount` может быть нецелым числом (например, 0.001) — и пройти проверку `amount > currentBid` при `currentBid = 0`. Нужно `parseInt` и проверка `amount >= 1`.
- **Фикс:**
```javascript
const amount = Math.floor(Number(body.amount));
if (!Number.isFinite(amount) || amount < 1) return res.status(400).json({ error: 'Invalid bid' });
```

**[SEC-04] Нет rate limiting**
- API открыт для flood-атак. Один пользователь может отправлять тысячи запросов в секунду.

**[SEC-05] Состояние комнаты передаётся полностью всем игрокам**
- Все видят `notifications`, `trades` (включая чужие pending trades), полный `properties` с чужими данными. Это by design для Монополии (информация открыта), но `trades` между другими игроками не должны быть видны до завершения.

## 4. ПРОБЛЕМЫ UI/UX И ФРОНТЕНДА

**[UI-01] Доска не адаптивна на маленьких экранах**
- Canvas фиксирован 760×760, масштабируется через CSS `width: 100%`. На телефонах с шириной 320px текст на клетках будет нечитаемым (9px / масштаб ≈ 4px). 
- **Решение:** Рисовать на canvas с учётом `devicePixelRatio` и увеличить размер текста; или сделать интерактивное поле с зумом.

**[UI-02] Нет индикации чей сейчас ход**
- Единственный индикатор — рамка вокруг HUD-блока. При 6 игроках на маленьком экране это легко пропустить. Нет заметного баннера "Ваш ход!" или вибрации.

**[UI-03] Кнопка "Завершить ход" показывается даже когда нужен повторный бросок (дубль)**
- Хотя сервер корректно установит `turnPhase = 'roll'` при `endturn` с дублями, UX странный: пользователь нажимает "Завершить ход", а ему говорят "бросайте снова". Лучше автоматически переходить к повторному броску.

**[UI-04] Отсутствие индикатора загрузки при API-вызовах**
- При нажатии кнопок нет loading state. Двойной клик → двойной API-вызов (двойная покупка, двойной бросок).
- **Фикс:** Дизейблить кнопки после нажатия до получения ответа.

**[UI-05] Модальные окна перекрывают важную информацию**
- Во время аукциона модалка "Имущество" может закрыть аукционный UI, и игрок пропустит возможность сделать ставку.

**[UI-06] Нет звуковых уведомлений**
- Telegram Mini App поддерживает `HapticFeedback`. При важных событиях (ваш ход, аукцион, оплата аренды) стоит использовать `tg.HapticFeedback.impactOccurred()`.

**[UI-07] Canvas не отображает цены клеток**
- Игрок не может узнать цену клетки до попадания на неё. Нет "тапни по клетке для деталей".

**[UI-08] Аукционный таймер может показывать отрицательные или неверные значения**
- `auctionInterval` вызывает API раз в секунду, но round-trip может занять >1 сек. Таймер мерцает или "застывает".

## 5. ПРОИЗВОДИТЕЛЬНОСТЬ

**[PERF-01] Canvas перерисовывается полностью при каждом render**
- `renderGame()` вызывается при каждом polling (каждые 2.5 сек) и каждом действии. `drawBoard()` перерисовывает все 40 клеток + все фигурки. На слабых телефонах — заметные лаги.
- **Решение:** Кешировать статическую часть доски (фон + подписи) в offscreen canvas. Перерисовывать только ownership/houses/players при изменении.

**[PERF-02] Полное состояние передаётся при каждом polling**
- Состояние комнаты может быть 20–50 KB. При 6 игроках и polling 2.5 сек — до 120 KB/сек входящего трафика на клиента.
- **Решение:** Diff-based updates или `lastUpdate` timestamp comparison (если не изменилось — пустой ответ).

**[PERF-03] `setInterval` для аукциона создаёт лишний HTTP трафик**
- Каждую секунду — GET запрос `auction_check`. При 5 игроках одновременно: 5 запросов/сек к серверу только для таймера.

## 6. РЕФАКТОРИНГ И УЛУЧШЕНИЯ

**[REF-01] Монолитный `api/game.js` — 500+ строк switch/case**
- Разделить на модули: `routes/`, `logic/game.js`, `logic/auction.js`, `logic/trade.js`, `storage/redis.js`.

**[REF-02] Отсутствие типизации**
- Добавить JSDoc types или перейти на TypeScript для отлова ошибок при компиляции.

**[REF-03] Магические числа разбросаны по коду**
- `200` (проход Старт), `50` (штраф тюрьмы), `1.1` (процент по залогу) — вынести в constants.

**[REF-04] Нет unit-тестов**
- Игровая логика (расчёт аренды, дубли, банкротство) — идеальна для unit-тестов. Вынести в pure functions.

**[REF-05] Клиентский код в одном HTML файле**
- 800+ строк JS inline. Разделить на модули (ES modules или бандлер).

### Исправление 2: Валидация Telegram initData

```javascript
// auth/telegram.js
const crypto = require('crypto');

function validateTelegramData(initData, botToken) {
  if (!initData) return null;
  
  const params = new URLSearchParams(initData);
  const hash = params.get('hash');
  if (!hash) return null;
  
  params.delete('hash');
  const dataCheckString = [...params.entries()]
    .sort(([a], [b]) => a.localeCompare(b))
    .map(([key, val]) => `${key}=${val}`)
    .join('\n');

  const secretKey = crypto
    .createHmac('sha256', 'WebAppData')
    .update(botToken)
    .digest();
  
  const computedHash = crypto
    .createHmac('sha256', secretKey)
    .update(dataCheckString)
    .digest('hex');

  if (computedHash !== hash) return null;

  // Check timestamp (allow 1 hour)
  const authDate = parseInt(params.get('auth_date'));
  if (Date.now() / 1000 - authDate > 3600) return null;

  return JSON.parse(params.get('user') || 'null');
}

module.exports = { validateTelegramData };
```

function nextTurn(room) {
  const activePlayers = getActivePlayers(room);
  if (activePlayers.length <= 1) {
    room.state = 'finished';
    room.winner = activePlayers[0]?.id;
    room.turnPhase = 'finished';
    return;
  }
  let next = (room.currentPlayerIndex + 1) % room.players.length;
  while (room.players[next].bankrupt) {
    next = (next + 1) % room.players.length;
  }
  room.currentPlayerIndex = next;
  room.turnPhase = 'roll';
  room.players[next].doublesCount = 0; // Reset for new turn
}

## РЕЗЮМЕ

Проект представляет собой хороший прототип с полной реализацией основных механик Монополии. Главные блокеры для production-ready состояния:

Первое — **in-memory storage не работает на Vercel** в принципе. Без Redis проект неработоспособен в деплое. Второе — **отсутствие валидации Telegram initData** делает API полностью открытым для подделки запросов. Третье — **аукционный таймер** зависит от клиентского polling, что ненадёжно. Четвёртое — есть несколько игровых багов (turnPhase при банкротстве, залог с домами в группе, doublesCount не сбрасывается), которые могут привести к "зависанию" игры.

После исправления P0 и P1 проблем проект будет функционально готов для beta-тестирования. P2 и P3 — это polish для production release.
